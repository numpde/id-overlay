Coupled Overlay UI State Model
==============================

Objective
---------
Define the conceptual state domains for the overlay UI in a way that matches
the current codebase and gives future simplifications one inspectable source of
truth.

This note is about state shape, not transition code.


Core Position
-------------
The UI should be modeled as one coupled state with four top-level domains:

- `session`
- `runtime`
- `panel`
- `status`

These are not independent systems. They are coupled, but they represent
different kinds of facts:

- durable overlay/session reality
- ephemeral interaction reality
- transient panel intent
- transient status override


Canonical Shape
---------------
The current canonical shape is:

```js
{
  session: {
    mode,
    opacity,
    image,
    placement,
    registration: {
      pins,
      solvedTransform,
      dirty,
    },
  },

  runtime: {
    pointer: {
      screenPx,
    },
    activeGesture,
    inputOverride,
  },

  panel: {
    intent,
  },

  status: {
    messageOverride,
  },
}
```

The corresponding vocabulary is defined in
[`src/core/ui-state-model.js`](../src/core/ui-state-model.js).


Why These Domains Exist
-----------------------
1. `session`

This is durable overlay reality:

- current mode
- current opacity
- whether an image session exists
- current manual placement
- current registration inputs and solved result

This is the state that persistence and rendering care about most.

2. `runtime`

This is ephemeral interaction reality:

- current pointer point in shared coordinates
- currently active sustained gesture, if any
- currently active input override, if any

This is not durable state. It exists to support interaction semantics.

3. `panel`

This is transient panel intent:

- idle
- paste armed
- clear-pins confirm
- clear-image confirm

This is not overlay reality. It is pending intent.

4. `status`

This is transient status override state:

- a temporarily forced message

The visible status text is otherwise derived from `session` and `runtime`.


Primary Facts vs Derived Views
------------------------------
The canonical model should contain primary facts only.

Examples of fields that should *not* be canonical because they are derived:

- `canCapturePointer`
- `passThroughActive`
- `pointer is inside the image`
- `current visible status message`
- `pinCount`
- `registration = empty | dirty | solved` as a second stored summary

Those may still exist as implementation conveniences elsewhere, but they are
not part of the conceptual state model.


Why Raw Registration Facts Stay in `session`
--------------------------------------------
The canonical model keeps:

- `registration.pins`
- `registration.solvedTransform`
- `registration.dirty`

instead of replacing them with a summary enum.

Reason:

- this note is meant to reflect the real canonical state shape, not a reduced
  abstraction that hides information the app actually stores and uses
- `pinCount` is derived from `pins.length`
- “empty / dirty / solved” is derived from the registration facts

So this note favors raw primary facts over summarized secondary labels.


Why `runtime` Is Shaped This Way
--------------------------------
`runtime` deliberately stores only:

- pointer position
- active gesture kind
- active input override

It does not store:

- derived pointer capability
- derived pass-through boolean
- hover-inside-image flags

The guiding rule is:

- keep only the ephemeral facts that interaction code actually needs as
  first-class runtime state
- derive the rest from policy and geometry


Why `panel.intent` Is Nested
----------------------------
The panel domain currently only stores one primary fact:

- `intent`

It still deserves its own domain because:

- it is conceptually distinct from overlay/session reality
- it is transient and timeout-driven
- future panel-specific state can grow there without polluting the top level


Why `status.messageOverride` Is Nested
--------------------------------------
The status domain currently only stores one primary fact:

- `messageOverride`

It remains nested for the same reason as `panel`:

- it is conceptually its own transient state domain
- it separates forced messages from the derived default status message


How This Should Be Used
-----------------------
This model should guide future refactors:

- `state.js`
  should map primarily onto `session`

- `interactions.js`
  should map primarily onto `runtime`

- `panel-state.js`
  should map primarily onto `panel`

- `status-controller.js`
  should map primarily onto `status`

- `presentation.js`
  should derive visible UI from these domains rather than inventing new state


What This Note Does Not Define
------------------------------
This note does not define:

- valid transitions
- transition tables
- reducer ownership
- button semantics
- solve-on-mode-switch policy

Those are separate concerns.

This note is only the shape and domain boundary reference.


Practical Rule
--------------
Before adding a new state field, ask:

1. Which of the four domains does it belong to?
2. Is it a raw fact or a derived view?
3. If it is derived, why is it being stored at all?

If that question cannot be answered cleanly, the field probably does not belong
in the canonical model.
